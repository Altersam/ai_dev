MCP, Skills и CLI: интерфейсы продукта для агентов

Как открыть продукт агентам через безопасные операции, понятные инструменты и тестируемые сценарии.

Главное в одном абзаце#

Александр Поляков предлагает рассматривать интерфейс для ИИ-агента как новый продуктовый интерфейс, наравне с веб-сайтом и мобильным приложением. Людям нужна удобная навигация и понятные формы, а агенту — компактные инструкции, явные операции, безопасная авторизация, предсказуемые результаты, понятные ошибки и возможность проверки. В докладе обсуждаются MCP, CLI, Skills и плагины: каждый механизм подходит для своих задач. Основной вопрос уже не в том, «можно ли агенту открыть страницу», а в том, «почему продукт не предоставляет официального, управляемого способа выполнять действие».

Тезис доклада: агентный интерфейс — самостоятельная точка контакта продукта с пользователем; он должен проектироваться, тестироваться и защищаться как полноценный API.

1. Почему браузерного доступа недостаточно#

Представьте задачу: найти железнодорожный билет для семьи с определёнными требованиями. Агент способен открыть сайт браузером, пройти по формам, отфильтровать результаты и предложить варианты. Но такой подход имеет слабые места: сессия авторизации может истечь, структура интерфейса измениться, часть действий потребует ручного подтверждения, а агент может неверно интерпретировать состояние страницы. Для массового продукта полагаться исключительно на управление мышью и скриншоты рискованно.

При этом браузер остаётся важным резервным способом взаимодействия, особенно пока нет официальных интеграций. Докладчик не предлагает его запретить: задача продукта — дать более надёжный и удобный путь. Например, вместо восьми экранов оформления разового пропуска — операцию create_pass с параметрами и машинно понятным ответом.

Редакторская аналогия. Для человека дверная ручка — интерфейс. Для промышленного робота лучше предусмотреть стандартный привод: ему незачем вращать ручку антропоморфным манипулятором, если система допускает штатную команду.

2. Три основных способа интеграции#

Механизм В чём суть Когда особенно полезен Ключевой компромисс
MCP Протокол предоставления инструментов и данных агенту Удалённый сервис, общий доступ нескольких клиентов, централизованное обновление Различия реализаций клиентов, вопросы контекста и авторизации
CLI Управление программой через команды терминала Локальные приложения, devtools, скриптуемая инфраструктура Требует среды исполнения и установки утилиты
Skill Описанная процедура с инструкциями и, иногда, скриптами Сложные регламенты, последовательные действия, предметные правила Надо доставлять и обновлять; инструкции потенциально опасны
Плагин / пакет Объединяет инструкции и инструменты Управляемая установка комплексной интеграции Совместимость и обновления на разных клиентах

Выбор не сводится к соревнованию технологий. Для облачного сервиса, которым пользователи управляют из разных приложений, логичен удалённый MCP. Для локального редактора файлов или генератора ресурсов — CLI. Если главная сложность не в вызове метода, а в процедуре подготовки и проверки — Skill. Иногда разумно предоставлять оба интерфейса: командную утилиту человеку и MCP — удалённому агенту.

3. Когда MCP предпочтительнее CLI#

У MCP есть архитектурный плюс: сервер может централизованно изменить состав инструментов и политику. Клиент при обновлении списка инструментов получит новые возможности без переустановки локального пакета. Для SaaS с десятками интеграций это важно.

Но нельзя обещать одинаковое поведение всех клиентов. Спикер обсуждает несовпадения в том, сколько инструкций и метаданных реально попадёт в контекст модели: часть клиентов сокращает содержимое, а длительные сессии могут сохранять устаревший набор инструментов. Поэтому инструкция не должна существовать только в длинном вступительном описании.

У CLI другая экономика: он естественно интегрируется в среду разработчика, его легко протестировать командами, а привычные --help, коды завершения и JSON-вывод делают поведение предсказуемым. Но обновление клиентов становится задачей распространения версий.

4. Как проектировать инструкции, чтобы они не терялись#

Длинная документация «на 40 экранов», отправленная агенту при подключении, может оказаться бесполезной: модель не прочтёт её целиком либо важная часть будет обрезана. Практический паттерн — короткое описание возможностей + точечный инструмент получения инструкций.

server.description: «Поиск и управление поездками».

get_instructions(topic="tickets.search")
    → требования к маршруту, детям, тарифам и фильтрам

get_instructions(topic="tickets.checkout")
    → последовательность подтверждения и оплаты

search_tickets(criteria)
    → список вариантов со стабильными ID

prepare_booking(ticket_id)
    → предварительная заявка без списания средств

Это редакторская иллюстрация подхода, а не реальное API Туту. Главное — дать возможность дочитать актуальные сведения в момент необходимости, а не загружать весь регламент заранее.

5. Операции по намерению, а не по таблицам базы данных#

Автоматический конвертер OpenAPI → MCP может опубликовать сотни методов и заставить агента самому собирать бизнес-процесс из низкоуровневых шагов. Результат — ошибки в порядке вызовов, лишние запросы и риск нарушить инварианты.

Спикер предлагает поднимать уровень абстракции. Не insertPaymentRow и updateOrderStatus, а prepareOrder, validateOrder, confirmOrder с понятными состояниями и отдельным человеческим подтверждением операции оплаты. Каждый инструмент должен быть малым, но достаточно высокоуровневым, чтобы одной транзакцией сохранить бизнес-правила.

Низкоуровневый интерфейс Интерфейс по намерению
GET /users, POST /cart, POST /reservation, POST /payment prepare_booking(...) → booking_draft_id
Агент сам угадывает порядок Порядок контролирует сервер
Ошибки требуют знания внутренностей Ошибка объясняет действие для исправления
Частичное состояние трудно откатить Черновик можно отменить до подтверждения

6. Понятные ошибки — часть интерфейса#

Сообщение 400 Bad Request не помогает агенту разобраться в проблеме. Гораздо полезнее структурированный ответ:

{
  "error": "pass_duration_out_of_range",
  "message": "Пропуск оформляется максимум на 2 часа",
  "valid_range_hours": [1, 2],
  "next_action": "Разбейте запрос на несколько пропусков или запросите согласование"
}

Пример редакторский. Ошибки полезно разделять на исправляемые агентом (неверный формат, пропущенный параметр) и требующие человека (покупка, доступ к закрытым данным, действие с правовыми последствиями). Недопустимо подсказывать агенту обход проверки прав.

7. Две версии интерфейса: для человека и машины#

При открытии адреса MCP обычный человек может увидеть пустую страницу или нечитаемый ответ. Но пользователю всё равно нужна публичная страница с возможностями сервиса, условиями подключения, авторизацией и документацией. В докладе приведён пример, когда ранний пользовательский тест показал именно такую проблему: сервис для агентов работает, но человек не понимает, куда попал.

Разумный дизайн: один домен, понятная HTML-страница для людей и корректные протокольные ответы для поддерживаемых клиентов. Человеческая документация должна объяснять, какие данные будет читать агент и какие действия потребуют дополнительного подтверждения.

8. Модель доверия и риск инструкции извне#

Skill, удалённый MCP и даже текст ответа API могут содержать инструкции, которые влияют на поведение модели. Сторонний пакет нужно проверять: что он читает, какие команды запускает, куда отправляет сведения, какая телеметрия встроена, кто поддерживает обновления.

Для удалённых инструментов важны более жёсткие меры: ограниченные OAuth-scopes, server-side авторизация, разделение чтения и изменения, журнал действий, изоляция недоверенного пользовательского контента, отсутствие прямого доступа к секретам и понятное подтверждение опасных шагов. Сами по себе «хорошие» инструкции в промпте не заменяют ограничения сервера.

Запомните: если агент получает письмо от неизвестного отправителя, текст письма — данные, а не инструкции с полномочиями изменять систему. Это пересекается с главой о безопасности AI-ядра.

9. Право, персональные данные и подтверждение действия#

Сервис, который только ищет справочные данные, отличается от сервиса, который регистрирует пользователя, оформляет бронирование или списывает деньги. Для последних необходимо отдельно продумать договорные условия, согласие на обработку персональных данных и момент, когда пользователь действительно подтверждает операцию.

В выступлении затронуты российские правовые вопросы, включая 152-ФЗ. Универсального разрешения «агент может всё, что может человек в браузере» не существует. Архитектура должна отражать категорию данных, цель обработки, основание доступа, хранение, аудит и отзыв разрешений. Конкретную юридическую схему необходимо согласовать с профильными специалистами.

10. Тестировать нужно пользовательские сценарии, а не только методы#

Даже если каждый endpoint проходит unit-тесты, полная последовательность может быть неправильной. Поэтому в проекте MCP для поездок команда прорабатывала реальные сценарии пользователей и тестировала их целиком. Спикер отмечает, что таким способом обнаруживались проблемы после первоначального запуска.

Пример матрицы тестов:

Сценарий Что проверяем Ожидаемый результат
Простое чтение Поиск с понятным фильтром Верный структурированный ответ
Неполные данные Не указан обязательный параметр Агент задаёт уточняющий вопрос
Истёкшая авторизация Протух токен Безопасное переподключение, нет скрытого обхода
Недоступный тариф Изменился внешний статус Корректная ошибка и альтернативы
Покупка Не было подтверждения Нет списания, заявка остаётся черновиком
Инъекция в описание Недоверенный текст содержит указания Инструкция игнорируется, данные остаются данными

Важно проверять трейсы: модель могла получить правильный ответ за счёт случайности, нарушения процесса или подмены шага. Итоговая оценка «успех» без анализа маршрута недостаточна.

11. Пошаговый план для своего продукта#

  1. Выберите три самые распространённые пользовательские задачи; измерьте их частоту и стоимость выполнения через веб-интерфейс.
  2. Выделите устойчивые бизнес-операции с идемпотентностью, понятными состояниями и правами.
  3. Определите, нужен ли локальный CLI, удалённый MCP, Skill или их сочетание.
  4. Сделайте минимальный набор инструментов по намерению пользователя, а не автоматически выгружайте весь API.
  5. Создайте короткие описания инструментов и отдельные подробные инструкции по темам.
  6. Поставьте ограничения на стороне сервера и журналируйте все изменения.
  7. Напишите минимум десять сквозных сценариев, включая отказ, ошибку и недоверенные данные.
  8. Проверьте продукт в нескольких агентных клиентах: трактовка инструкций и ограничения могут различаться.
  9. Добавьте понятную страницу подключения для людей и канал поддержки.
  10. Смотрите реальные трейсы, исправляйте контракт и контролируйте регрессии.

Задание#

Возьмите существующий образовательный веб-сервис: запись на консультацию, просмотр домашнего задания или выдача справки. Опишите три операции для агента, разделите readonly и write-права, добавьте сценарий отказа, определите, какое действие всегда должен подтверждать пользователь. Затем нарисуйте «человек → агент → шлюз → сервис → журнал». Это и есть черновик agent-facing интерфейса.

Связанные главы: AI-ядро организации, Защита данных, Контроль качества, Evidence-based SDLC.
