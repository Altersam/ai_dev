Свой инференс для агентов: GPU, контекст, кэш и задержки

Почему сервер с мощными GPU может давать плохой отклик — и какие метрики, архитектурные решения и проверки действительно важны для агентных нагрузок.

Важный поворот: агент чаще «читает», чем «пишет»#

В разговоре об инференсе часто сравнивают число токенов генерации в секунду. Для обычного чата это заметная характеристика. Для агентной системы, которая на каждом шаге подаёт модели большой системный контекст, описания инструментов, историю и результаты предыдущих операций, всё сложнее.

Валерий Ковальский объясняет, что значительная часть вычислительной работы приходится на обработку входных токенов. Поэтому хороший сервер для диалогов может оказаться плохим сервером для длинных агентных сессий: дело не только в количестве GPU, но и в том, как движок распределяет память и повторно использует уже обработанные префиксы.

Основная мысль доклада: прежде чем покупать железо или оптимизировать токены генерации, изучите профиль реальных запросов, долю повторяемого контекста, время до первого токена и причины промахов кэша.

1. Три стадии ответа модели#

Prefill — обработка входа#

Модель получает промпт: системные правила, инструкции, историю, пользовательский запрос и материалы из инструментов. На этапе prefill она обрабатывает входные токены и формирует промежуточные представления, нужные для последующей генерации.

Decode — генерация ответа#

После prefill модель выдаёт новые токены по одному или небольшими блоками. Этот этап называют decode. Пользователь обычно видит его как «печать ответа».

KV-cache — память о предыдущих вычислениях#

Во время обработки контекста движок хранит ключи и значения механизма внимания — KV-cache. Если несколько запросов имеют общий префикс, подходящий движок может использовать готовую часть вычислений вместо повторной обработки одинакового начала.

  [ System + Tools + Rules ] [ History ] [ New question ]
             │                   │            │
             └──────── PREFILL ──┴────────────┘
                           │
                      KV-CACHE
                           │
                         DECODE
                           │
                  ответ агента / tool call
                           │
                  НОВЫЙ ШАГ АГЕНТА
           прежний контекст + результат инструмента

Аналогия. Если каждый раз перед вопросом вам зачитывают учебник на 500 страниц, вы будете тратить время не на формулирование ответа, а на повторное чтение. Кэш помогает не перечитывать одинаковую часть. Но только если система узнаёт, что она действительно одинаковая.

2. Почему длина контекста влияет на стоимость#

Контекст агента часто включает:

  • правила и роль;
  • описания доступных инструментов;
  • историю событий и ответов;
  • содержимое файлов и результатов поиска;
  • предыдущие наблюдения и планы;
  • данные о состоянии задачи.

Чем больше материалов в каждом запросе, тем выше требования к памяти и вычислениям. Спикер приводит собственные наблюдения о существенном перевесе входных токенов над выходными. Не следует переносить его конкретные соотношения на любую модель и продукт: правильное значение нужно измерять на ваших журналах запросов.

Инженерный вывод#

Оптимизация полезна на уровне контекстной политики, а не только железа. Подгружайте инструмент по необходимости, не вставляйте целиком тысячестрочные логи, храните долговременное состояние отдельно, минимизируйте повторение длинных неизменных данных.

3. Почему кэш легко потерять#

Кэш префиксов работает, когда начало запроса совпадает по содержимому и формату с уже обработанной последовательностью. Мелкое изменение может уничтожить совпадение: вставили текущую дату в начале системной инструкции, переставили описание инструментов, изменили порядок правил, отформатировали текст другим способом.

Запрос A:
[STABLE RULES][TOOLS][HISTORY_A][QUESTION]
       └───────────────┘
          повторяемая часть

Запрос B:
[NEW DATE][STABLE RULES][TOOLS][HISTORY_B][QUESTION]
           └─ прежний префикс больше не совпадает

Полезные практики:

  1. Размещайте стабильные правила и описания инструментов в одинаковом порядке.
  2. Добавляйте временные значения и прочую динамику ближе к концу, если архитектура это допускает.
  3. Не меняйте сериализацию JSON и порядок элементов без нужды.
  4. Разделяйте варианты системных промптов и измеряйте cache hit rate.
  5. Проверяйте кэш на настоящих многоходовых агентных сессиях, не только на коротких синтетических запросах.

4. Роутинг запросов: одинаково загруженные GPU ≠ быстрые GPU#

Если балансировщик равномерно распределяет запросы по всем узлам, один и тот же агент в разные моменты попадает на разные серверы. На новом узле его прежний контекст может оказаться холодным. Поэтому балансировка исключительно по «наименьшей очереди» нередко проигрывает маршрутизации с учётом кэша.

Сравнение двух стратегий#

Стратегия Плюс Минус
Round-robin / least-loaded Равномерная нагрузка Не учитывает уже загруженные префиксы
Session affinity Выше шанс повторно использовать кэш Риск перегрузки одного узла
Cache-aware routing Может выбирать узел по локальности контекста Сложнее и требует достоверной телеметрии

Ловушка: роутер может считать, что нужный префикс существует, хотя движок его уже вытеснил из памяти. Поэтому нужны метрики реального попадания в кэш, а не только намерение балансировщика.

5. Горячий, тёплый и холодный контекст#

Упрощённая модель:

  • Горячий: данные контекста доступны непосредственно для быстрой обработки.
  • Тёплый: часть состояния хранится вне самой быстрой памяти и может быть загружена с дополнительной задержкой.
  • Холодный: контекст приходится обрабатывать заново.

В докладе обсуждаются решения с более ёмкой оперативной памятью и другими способами удержания кэша. Такие схемы могут улучшать задержки, но зависят от конкретного движка, интерфейса памяти, пропускной способности и того, как именно поддерживается перемещение кэша.

Вывод: недостаточно знать суммарный объём VRAM. Нужно понимать, сколько памяти реально остаётся под KV-cache после загрузки весов и обслуживания параллельных запросов.

6. Какие метрики нужны для реального сервиса#

Метрика Значение Что показывает
TTFT Time to First Token Время от запроса до первого токена
P50, P95, P99 Процентили задержки Типичное и худшее пользовательское переживание
Input tokens/s Скорость обработки входа Насколько тяжёлые префиксы обслуживаются
Output tokens/s Скорость генерации Как быстро появляется текст после prefill
Cache hit rate Доля полезных попаданий в кэш Сколько контекста повторно используется
Queue time Время ожидания перед выполнением Признак нехватки мощности или плохого планирования
Concurrency Число одновременных сессий Реальное распараллеливание нагрузки
OOM / errors Ошибки памяти и исполнения Устойчивость сервиса
Cost / useful task Цена законченного задания Связь технических метрик с полезным результатом

Почему P95 важнее «лучшего результата»#

Средний TTFT в 3 секунды может скрывать то, что каждый двадцатый запрос ждёт почти минуту. Для человека, управляющего несколькими агентами, такие задержки часто важнее пиковой скорости сервера в лаборатории.

Для SLA фиксируйте диапазон нагрузки, длину входа, форму многоходового трафика, качество ответов и условия, при которых были получены показатели.

7. Честный бенчмарк GPU-системы#

Большая ошибка — объявить результатом сервера максимальную скорость одной короткой генерации. Это не отражает работу нескольких длительных сессий с разными промптами, инструментами и кэшем.

Рекомендуемый протокол тестирования (редакторская адаптация принципов доклада):

  1. Выберите 3–5 реальных сценариев: поиск, написание кода, проверка, длинный диалог, многошаговый агент.
  2. Зафиксируйте распределение длины входных и выходных токенов.
  3. Создайте смесь повторяющихся и уникальных префиксов.
  4. Прогоните разные уровни параллелизма.
  5. Измерьте TTFT P50/P95/P99, ошибки, очередь, пропускную способность.
  6. Сравните качество решения задач, а не только скорость.
  7. Повторите после смены квантования, контекстной политики и роутера.

Демонстрационная таблица результатов#

Все числа ниже иллюстративные, а не результаты Валерия:

Параметр Стенд А Стенд Б
Выходных токенов/с 58 44
TTFT P95 при высокой нагрузке 47 с 13 с
Cache hit rate 29% 81%
Завершённых задач/час 18 31

По одному показателю «токены/с» быстрее А; по пользовательскому опыту и реальной продуктивности может выигрывать Б. Именно ради такой оценки требуется многомерный тест.

8. Квантизация и выбор размера модели#

Квантизация уменьшает точность представления весов и/или операций, снижая требования к памяти и иногда повышая скорость. Но одинаковое формальное качество на одном тесте не гарантирует устойчивость в другом домене.

Спикер рекомендует осторожно подходить к нестандартным квантованным сборкам, особенно когда сервис обслуживает неизвестные заранее задачи. Возможные потери проявляются неравномерно: модель остаётся хороша в диалогах, но хуже следует формату JSON или реже правильно вызывает инструменты.

Подход Выгода Что проверять
Полная / высокая точность Максимально близко к исходной модели Бюджет VRAM и пропускная способность
Официальная низкая точность Экономия ресурса Совместимость с железом и качество в вашем домене
Агрессивная сторонняя квантизация Возможность запуска на меньшем числе GPU Tool calling, длинные задачи, численные ошибки, регрессии

Нет универсальной лучшей квантовки. Для одной учебной классификации разница может быть незаметна, для сложной агентной маршрутизации — критична.

9. Роль Head of Inference#

В докладе звучит мысль о формировании новой инженерной роли: специалиста, который связывает продукт, агентную платформу, инфраструктуру и экономику инференса.

Ему нужно понимать:

  • как устроен запрос от приложения к модели;
  • почему длинный контекст и кэш влияют на пользовательский опыт;
  • как работают движки исполнения и балансировщики;
  • какие цели качества предъявляет сам продукт;
  • сколько стоит нагрузка и как измеряется окупаемость;
  • что происходит при деградации, отказе узла и всплеске запросов.

То есть этот специалист не просто «следит за видеокартами», а отвечает за качество эксплуатации интеллекта как сервиса.

10. Что это означает для локального учебного кластера#

Предположим, в организации есть несколько десятков GPU-станций. Соблазнительно сложить объём видеопамяти и представить, что получится одна огромная видеокарта. Это не так: физически распределённые GPU не образуют общую VRAM автоматически, а при запуске большой модели важны межузловые соединения, параллелизм, память каждого ускорителя и поддержка используемого стека.

Рациональный пилот может идти по двум веткам:

Ветка А — несколько независимых моделей: каждый узел обслуживает свою модель или часть запросов; нагрузку распределяет маршрутизатор. Хорошо для параллельных лёгких задач и экспериментов.

Ветка Б — одна распределённая модель: требуются поддержка tensor/pipeline parallelism и подходящие межсоединения; обычный Ethernet может стать серьёзным ограничением. Нужны отдельные бенчмарки.

Для образовательных задач нередко практичнее начать с небольшой/средней модели, RAG и качественных инструментов, чем пытаться немедленно поднять максимальную LLM на всех GPU.

11. План первого эксперимента#

  1. Соберите 100–200 анонимизированных или синтетических реальных по структуре запросов.
  2. Отделите короткий чат от агентного потока с длинной историей.
  3. Замерьте базовые метрики и число успешно завершённых заданий.
  4. Измените только один параметр: порядок промпта, тип роутинга или квантование.
  5. Повторите тест и зафиксируйте как выигрыш, так и регрессии.

Чек-лист:

  • TTFT измеряется на реальной агентной нагрузке.
  • Считаются P95 и P99, а не только среднее.
  • Измеряется реальный cache hit rate.
  • Квантизация проверена на tool calling и многошаговых задачах.
  • Стоимость вычислений соотнесена с качеством результата.
  • Учитываются приватность, сеть и хранение контекста.

Вопрос для самопроверки. Почему добавление ещё одного GPU может не уменьшить задержку? Потому что проблема может находиться в роутинге, очереди, промахах кэша, сети или модели работы с контекстом, а не в суммарной мощности.
