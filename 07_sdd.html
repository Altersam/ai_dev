Как управлять большим агентно-разрабатываемым проектом, не утонув в Markdown-файлах, и когда спецификация действительно стоит затраченного времени.

Что такое SDD и почему это больше, чем длинный промпт#

Spec-Driven Development (SDD) — подход, при котором до реализации формируется явное описание желаемого поведения системы, ограничений, ключевых решений и критериев проверки. Агент не просто выполняет «сделай как-нибудь», а работает по документированному намерению.

Егор Толстой подчёркивает: SDD — не магический новый язык программирования и не обещание, что «документация теперь всегда актуальна». Это инженерный способ снизить неопределённость и управлять сложностью, особенно когда исполнение стало дешёвым и быстрым, а ошибки понимания — дорогими.

Главный тезис: важнейшая роль спецификации — не заставить модель лучше писать код, а сделать так, чтобы вы и агент одинаково понимали, какую проблему следует решить.

1. Три проблемы, которые SDD помогает решать#

Ограничение эффективного контекста#

Номинально модель может принимать очень большой контекст. Но это не означает, что все детали длинной переписки будут одинаково надёжно учитываться в конце работы. Со временем накапливаются отвлекающие результаты инструментов, компромиссы и устаревшие предположения.

Спецификация позволяет перенести устойчивые решения в компактный внешний артефакт: новый агент читает короткую актуальную суть, а не всю историю исследования.

Недостаточно выраженный intent#

Человек знает, какой результат ему нравится, но редко полностью выражает это в первом запросе. Модель заполняет недосказанное собственными решениями, которые могут оказаться неверными. В SDD сначала уточняют требования, исключения, границы и критерии, затем поручают реализацию.

Когнитивная нагрузка при параллельной работе#

Когда одновременно работают несколько агентов, человек вынужден помнить, какие решения были согласованы в каждой ветке. Спецификации уменьшают зависимость от кратковременной памяти и помогают возвращаться к задаче после перерыва.

Важно: не все эти проблемы одинаково сильны для всех проектов. Для небольших правок избыточный SDD-процесс может стать хуже простого диалога.

2. Как выглядит минимальный цикл SDD#

   ПРОБЛЕМА / ИДЕЯ
         │
         ▼
   ИССЛЕДОВАНИЕ КОНТЕКСТА
         │
         ▼
   УТОЧНЕНИЕ НАМЕРЕНИЯ
         │
         ▼
    СПЕЦИФИКАЦИЯ
   требования + ограничения
         │
         ▼
   ПЛАН / СРЕЗЫ РАБОТЫ
         │
         ▼
     РЕАЛИЗАЦИЯ
         │
         ▼
   ПРОВЕРКА ПО СПЕКЕ
         │
         ▼
    ПРИЁМКА / АРХИВ

На каждом этапе есть отдельный результат. Это полезно при смене модели, сбросе контекста или передаче работы другому агенту: следующая сессия получает подготовленный материал, а не пересказ «что мы там обсуждали».

3. Какой должна быть хорошая спецификация#

Не существует универсального числа страниц. Есть набор вопросов, на которые желательно ответить.

Раздел Что нужно описать
Проблема Какую реальную потребность закрываем
Scope Что входит и не входит в изменение
Пользовательские сценарии Кто и каким образом использует функцию
Критерии готовности Как независимо подтвердить успех
Инварианты Что обязательно сохранить неизменным
Совместимость Какие старые данные и API продолжают работать
Дизайн Почему выбрано это решение и какие альтернативы отклонены
Риски Что может пойти не так
Проверки Какие тесты подтверждают каждый критичный пункт

Пример: небольшая спека#

# Функция: импорт результатов тестирования из Excel

## Цель
Учитель загружает XLSX; система сопоставляет ID с классом
и создаёт отчёт по классам без изменения исходных баллов.

## В границах задачи
- XLSX и проверка обязательных столбцов;
- сопоставление по ID;
- отдельный лист «Не найдено»;
- протокол дубликатов.

## Вне задачи
- изменение исходных баллов;
- отправка отчёта по почте;
- автоматическое объединение похожих ФИО.

## Критерии готовности
1. Все найденные ID попадают в нужный класс.
2. Неизвестные ID явно перечислены.
3. Суммы по классам и исходному файлу совпадают.
4. Повторный импорт одного файла не создаёт дубли.
5. Исходный файл сохраняется неизменным.

Это учебный пример, созданный для книги. Ценность здесь в проверяемости: агент не может считать задачу завершённой, если исчезла часть учеников или поменялись исходные результаты.

4. Связь спецификации с тестированием#

Важнейшее преимущество SDD — тесты можно генерировать не по готовому коду, а по требованиям. Иначе агент может написать тесты, которые идеально подтверждают его собственную неверную реализацию.

Требование → сценарий → тест#

Функция: импорт Excel

  Сценарий: неизвестный идентификатор
    Дано: справочник содержит ID 1 и ID 2
    И файл содержит ID 1 и ID 99
    Когда пользователь импортирует файл
    Тогда запись с ID 1 получает свой класс
    И ID 99 находится в отчёте «Не найдено»
    И исходные баллы не меняются

Такой формат напоминает BDD — Behavior-Driven Development. Не обязательно использовать Gherkin буквально. Смысл в том, чтобы наблюдаемое поведение связывалось с отдельной проверкой.

5. Когда спека окупается, а когда нет#

Используйте SDD, если:

  • изменения затрагивают несколько модулей и людей;
  • есть существенная неоднозначность требований;
  • потенциальный дефект дорог;
  • проект старый, а структура сложная;
  • работу будут делать разные агенты в несколько этапов;
  • решения нужно объяснять и сопровождать спустя месяцы.

Скорее не используйте полный процесс, если задача сводится к исправлению опечатки, замене одной ссылки или однозначной локальной правке с простой проверкой.

Полезный фильтр#

Спросите: «Сколько времени уйдёт на исправление неверного решения, если мы сейчас не уточним задачу?» Если цена ошибки выше стоимости короткой спеки — она, вероятно, оправдана.

6. Инструментальные подходы: чем отличаются#

Егор обсуждает несколько популярных семейств инструментов. Названия ниже приведены в нормализованном написании; подробности конкретных версий нужно сверять с актуальной документацией.

Подход Характер Кому подходит
OpenSpec Относительно лёгкая работа с изменениями и спецификациями Командам, которым нужна ясность без тяжёлого процесса
Superpowers Коллекция инженерных навыков, планирования и проверок Тем, кто хочет усилить существующий процесс отдельными практиками
BMAD Method Более структурированная цепочка ролей и артефактов Большим или новым продуктовым инициативам с высокой сложностью
Spec Kit / подобные toolkit Шаблоны и команды вокруг спецификаций Тем, кому важна стандартизация процесса
Собственный лёгкий шаблон Только нужные команде файлы и правила Небольшим командам, хорошо понимающим свои требования

Осторожно с выбором: популярность и число команд в toolkit не доказывают эффективность. По докладу, избыток процедур способен съедать время и внимание.

7. Brownfield — что сложнее, чем в новом проекте#

Brownfield — система с существующим кодом, историей решений, пользователями, данными и неочевидными ограничениями. В новом проекте можно сравнительно легко принять архитектуру с нуля; в старом даже маленькая функция может затронуть устаревшие API, миграции и чужие договорённости.

Главная задача перед изменением — узнать уже существующие инварианты:

  • какие данные нельзя менять или терять;
  • какие интеграции зависят от старого поведения;
  • какие решения записаны только в коде и тестах;
  • какие ограничения связаны с развёртыванием;
  • какие модули используют общий формат данных.

Минимальный «паспорт» изменения#

Хороший план для brownfield содержит: описание текущего поведения, список затронутых контрактов, изменения для обратной совместимости, стратегию миграции, список тестов, план отката и ответственного за приёмку.

8. Живые спецификации: почему документ не становится абсолютной истиной#

Звучит привлекательно: «У нас есть спецификация, значит, всегда знаем, как система работает». Но реальный проект меняется десятками мелких правок, многие из которых проходят без полноценного SDD. Через несколько месяцев документы могут устареть.

В докладе обсуждается практичная позиция:

  • относитесь к спекам как к истории замыслов и решений, а не к гарантированной копии системы;
  • актуальность фактического поведения проверяйте тестами, кодом и работающим продуктом;
  • используйте архивирование и периодическую очистку неактуальных документов;
  • ключевые архитектурные решения и публичные контракты храните дольше, чем мелкие рабочие планы.

Опасность: если «источником истины» объявили старый документ, агент способен восстановить поведение, которое продукт уже давно перестал поддерживать.

9. Где хранить спеки и нужно ли их коммитить#

Зависит от структуры разработки:

  • при монорепозитории и локальных изменениях — рядом с кодом;
  • если изменения охватывают несколько независимых репозиториев — возможно, в отдельном репозитории;
  • если вы только тестируете внедрение SDD — начните с временных артефактов и не загрязняйте основную кодовую базу автоматически;
  • для важных решений используйте понятные имена и связывайте документы с тикетами и версиями.

Пример структуры:

specs/
├── active/
│   └── 2026-11-excel-import/
│       ├── intent.md
│       ├── design.md
│       ├── tasks.md
│       └── acceptance.md
├── decisions/
│   └── ADR-008-data-contract.md
└── archive/
    └── ...

Плохая практика — хранить одновременно несколько взаимно противоречащих папок со «спеками», которые разные агенты воспринимают как актуальные.

10. Стоит ли пересматривать спеки вместо кода#

Для крупных изменений ревью спецификации до реализации часто дешевле исправления уже написанного модуля. Особенно когда проверяют архитектуру, совместимость и соответствие бизнес-замыслу.

Но spec review не заменяет code review и тесты. Спецификация может быть отличной, а реализация — ошибочной; или наоборот, технически хороший код решит другую задачу.

Практичное разделение:

  • Spec review: что делаем, зачем, какие альтернативы, что запрещено, как проверяем.
  • Code review: действительно ли реализация соблюдает ограничения, нет ли дефектов и технического долга.
  • Acceptance: получила ли организация нужный результат.

11. Как внедрить SDD без бюрократии#

Эксперимент на трёх задачах: выберите одну сложную, одну среднюю и одну простую. Для сложной сделайте полный цикл; для средней — компактный SPEC.md; для простой — обычный план и тест. Сравните время до принятого результата, число переделок, субъективную нагрузку и количество неучтённых решений.

Результатом будет собственное правило выбора процесса, а не новая обязанность «писать 30 файлов для каждой задачи».

Чек-лист:

  • Спека описывает поведение, а не красивый текст про архитектуру.
  • Есть явный scope и out-of-scope.
  • Критерии готовности проверяемы.
  • Для старого проекта изучены зависимости и совместимость.
  • Тесты связаны с требованиями.
  • Документы архивируются, устаревшие версии не выдаются за истину.
  • Процесс облегчает работу, а не превращается в самоцель.

Вопрос для самопроверки. Нужен ли SDD, если новая модель научится идеально писать код? Да, если людям всё ещё нужно согласовать намерение, ответственность и решения; нет, если для конкретной простой задачи дополнительных согласований не требуется.
